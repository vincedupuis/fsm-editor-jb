# FSM Editor for JetBrains IDEs

IntelliJ Platform plugin (2024.3+, all JetBrains IDEs with XML and JSON support): a visual editor for UML 2.5.1 state machines. A machine is two JSON files: `X.fsm`, the model (no ids: elements are identified by their names), and `X.fsm.layout`, the drawing. The model file's format is fsm-cli's (its README, its schema and test cases); the layout file's is fsm-editor-common's (its `schemas/fsm-layout.schema.json`). Files of earlier versions are XMI 2.5.1 with UML DI: they are read, and converted when changed. It is the JetBrains edition of FSM Editor for VS Code (`../fsm-editor-vscode`) and FSM Editor for Visual Studio (`../fsm-editor-vs`): same concepts, rules and messages. Reading and writing the files, converting old ones, validation, the grammar's checks, comparing, merging and code generation are fsm-editor-common's (`../fsm-editor-common`, Rust), run as a sidecar process (`fsm-editor-common serve`); this edition keeps the UI, the diagram's geometry and editing (Kotlin, a port of the Visual Studio edition's C# Core), and the IDE's integration.

## Commands

```sh
./gradlew :core:test          # core tests: the client of fsm-editor-common (its interface's cases, plugin/cli/api-cases), editing, extraction, traces, and GeometryTest: SvgExport against core/src/test/geometry, a copy of the VS Code edition's reference SVGs (its test/unit/fixtures/geometry)
./gradlew :plugin:test        # headless IDE tests; also paints the editor into plugin/build/screenshots/*.png
./gradlew :plugin:runIde      # sandbox IDE with the plugin; try examples/MediaPlayer.fsm and examples/Order.fsm (uses Payment.fsm)
./gradlew :plugin:buildPlugin :plugin:verifyPlugin [-PverifyIde=<local IDE path>]
scripts/fetch-common.sh [--build] [<dir>]  # copy fsm-editor-common's sidecar into plugin/cli/<platform>, fsm-cli's templates, schemas/ and api-cases/ into plugin/cli (from ../fsm-editor-common + ../fsm-cli, or a folder of unpacked release archives; gitignored); the tests need the sidecar
```

## Architecture

- `core` (Kotlin/JVM, no IntelliJ references; the IDE supplies the Kotlin stdlib at run time) holds all the logic:
  - `Model.kt`: `FsmModel`, a flat vertex list where `parent` is a region id, or a state id for border vertices (entry/exit points of a state, connection point references). Entry/exit points whose parent is a top-level region are the machine's own connection points. `ModelIndex` gives tree navigation. Vertices and transitions are compared by identity.
  - `Common.kt`: the client of fsm-editor-common's sidecar: started on first use (`Common.executablePath`, else the system property `fsm.common` (the tests), `FSM_EDITOR_COMMON`, or the plugin's `cli/<platform>/` beside its `lib/`), one JSON request per line, answered in order, one at a time, started again when it exits; it ends with the IDE (its input closes). `ModelJson.kt`: the model as the JSON the sidecar takes and gives (vertices and transitions as `ClipboardJson` writes them).
  - Facades over the sidecar, keeping their signatures (ports of the C# ones): `Format.kt` (`readMachine`, `writeMachine`, which gives generated names and resolves references, `derivedIds`; the small helpers stay here), `MachineFiles.kt`, `Conversion.kt`, `Load.kt`, `Validation.kt`, `Expressions.kt`, `Compare.kt`, `Merge.kt`. `Num.kt`: numbers as JavaScript writes them.
  - Staying here: `Labels.kt` (transition label syntax), `Geometry.kt` (compartments, regions, routes, labels), `DiagramSession.kt` (every editing operation, calling the `onCommitted` listeners), `Tools.kt`, `SvgExport.kt`, `ClipboardJson.kt` (same clipboard JSON as the other editors, and a small JSON reader, `PlainJson`), `Workspace.kt` (hrefs, machine summaries, submachine resolution), `Sessions.kt` (the logic of the diff and merge panes), `Extraction.kt`, `Trace.kt` (the Trace Player: log formats, replay, and `TraceSession`, the logs, timeline and cursor).
- `plugin` (IntelliJ Platform Gradle Plugin 2.x, compiled against IC 2024.3):
  - `FsmEditorProvider` (`PLACE_BEFORE_DEFAULT_EDITOR`) adds the Diagram tab before the Text tab. `.fsm` files are `FsmFileType` (a `JsonFileType`), old ones `OldFsmFileType` (XML, told apart by their content); `*.fsm.layout` is mapped to JSON. `FileSource` (`editor/DiagramSource.kt`) is a machine over the IDE's documents of its two files: its state is read from their texts (the same texts give the same state object), a diagram edit writes both documents as one `WriteCommandAction`, and save, the modified mark and undo/redo are the IDE's (`FsmFileEditor` implements `DocumentReferenceProvider` over both). Opening changes nothing; an old file is converted at the first edit, and the files linked to it when it is saved; an unreadable layout file is replaced only after asking, at the first edit. `DiagramPane` is a diagram over a source (validation in a non-blocking read action against the machines found by `FsmWorkspace`, the Trace Player's ids mapped with `derivedIds`). A file with merge conflicts opens as the diagram merge in its Diagram tab (`FsmFileEditor`: result, incoming, current); Compare as Diagrams is a `FrameDiffTool` (`editor/DiagramDiff.kt`) shown by the IDE's diff view; both link panes through Core's `MergeSession`/`DiffSession`, and `services/Git.kt` runs git.
  - `editor/`: Swing built in code. `DiagramCanvas` paints with Java2D and hit-tests geometrically; `PropertiesPanel` rebuilds itself per selection; `Theme` maps IDE/editor-scheme colors; `ToolIcons` draws the toolbox icons.
  - Copy/Cut/Paste/Delete come from the IDE actions through `DiagramCanvas.uiDataSnapshot` (only while the canvas has the focus); other keys are handled by the canvas.
  - `services/FsmAnnotator` reports the problems of a model file that can't be read, and validation at the line of each element (an old file's at its `xmi:id`), in the Text tab and the Problems view; `FsmSchemas` gives the Text tab the JSON Schemas (`cli/schemas`: fsm-cli's for `.fsm`, fsm-editor-common's for `.fsm.layout`); `FsmResources` makes the XML support ignore the XMI/UML namespaces of old files. `FsmWorkspace` also renames or moves a layout file with its model file.
  - `trace/`: `TracePlayerService` (project service) runs a `TraceSession` (polls the logs' size and time to follow them, play timer, machines of the project and open documents) and hands each open diagram its `TraceView`, drawn by `DiagramCanvas`; `TracePlayerWindow.kt` is the Trace Player tool window.
  - `codegen/CodeGenerator.kt`: code generation through the sidecar's `generate` (fsm-cli's generator): the machine's text and those of its submachines (from disk, transitively), the template's text; the files that come back are written into the output folder. The release workflow bundles the sidecar per platform in `plugin/cli/<platform>/`, fsm-cli's templates in `plugin/cli/templates` and the schemas in `plugin/cli/schemas`, from the fsm-editor-common release pinned by `FSM_COMMON_VERSION`, and runs the tests with its interface's cases. `CodeGeneration.generate` is the whole flow; output goes to the FSM Code Generation tool window.

## Project rules

- Keep parity with the VS Code and Visual Studio editions for the UI: editor behavior, clipboard JSON. The file format, the grammar, validation, conversion, comparing and merging are fsm-editor-common's and fsm-cli's: don't reimplement them here; change them there, then `scripts/fetch-common.sh --build` and `./gradlew :core:test`. `core` ports the Visual Studio edition's C# Core file for file, so port a change from there. `Geometry.kt` mirrors `media/editor.js` of the VS Code edition: compare it by hand, for example with the screenshots from `:plugin:test`.
- **Text grammar:** behaviors are argument-less calls separated by `;`; conditions combine calls with `!`, `&&`, `||` and parentheses; `else` only on choice/junction branches; triggers are event names or `after(<number><ms|s|m|h>)`. The editor refuses invalid text, and the validator reports it.
- **Out of scope:** state machine extension/inheritance and the transition-oriented notation.
- Don't reimplement code generation: templates and the code model belong to fsm-cli.
- `.fsm` files hold no model hash: fsm-cli computes it from the file.
- Core must not reference IntelliJ classes. Keep the plugin free of internal, override-only and experimental API: `verifyPlugin` must report "Compatible" with no such usages (Kotlin compiles with `-jvm-default=no-compatibility` so implementations of platform interfaces don't re-declare their default methods). Kotlin API level stays at 2.0 (the stdlib of 2024.3).
- User-facing docs: `README.md`, `docs/UML-CONFORMANCE.md` (update when behavior or rules change), `docs/CODEGEN.md`.
