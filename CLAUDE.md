# FSM Editor for JetBrains IDEs

IntelliJ Platform plugin (2024.3+, all JetBrains IDEs with XML and JSON support): a visual editor for UML 2.5.1 state machines. A machine is two JSON files: `X.fsm`, the model (no ids: elements are identified by their names), and `X.fsm.layout`, the drawing. The model file's format is fsm-cli's (its README, its schema and test cases); the layout file's is the editions' own, defined by the VS Code edition (its `docs/UML-CONFORMANCE.md`, "The layout file", and `schemas/fsm-layout.schema.json`, copied here). Files of earlier versions are XMI 2.5.1 with UML DI: they are read, and converted when changed. It is the JetBrains edition of FSM Editor for VS Code (`../fsm-editor-vscode`) and FSM Editor for Visual Studio (`../fsm-editor-vs`): same concepts, file format, rules and messages, reimplemented in Kotlin (a port of the Visual Studio edition's C# Core; no JavaScript is reused). Code generation runs `fsm write`, the Rust command-line tool of `../fsm-cli`, with Jinja templates.

## Commands

```sh
./gradlew :core:test          # core tests: fsm-cli's test cases (plugin/cli/cases), the layout fixtures, parity with the VS Code reference results
./gradlew :plugin:test        # headless IDE tests; also paints the editor into plugin/build/screenshots/*.png
./gradlew :plugin:runIde      # sandbox IDE with the plugin; try examples/MediaPlayer.fsm and examples/Order.fsm (uses Payment.fsm)
./gradlew :plugin:buildPlugin :plugin:verifyPlugin [-PverifyIde=<local IDE path>]
scripts/fetch-cli.sh [--all] [--build] [<dir>]  # copy fsm + templates into plugin/cli/<platform>, schemas/ and cases/ into plugin/cli (from ../fsm-cli, or --all from a folder of unpacked release archives; gitignored); the core tests need cases/
```

## Architecture

- `core` (Kotlin/JVM, no IntelliJ references; the IDE supplies the Kotlin stdlib at run time) holds all the logic:
  - `Model.kt`: `FsmModel`, a flat vertex list where `parent` is a region id, or a state id for border vertices (entry/exit points of a state, connection point references). Entry/exit points whose parent is a top-level region are the machine's own connection points. `ModelIndex` gives tree navigation. Vertices and transitions are compared by identity.
  - `Json.kt` + `Format.kt`: the file format, a port of the C# `Json.cs`/`Format.cs` (the VS Code edition's `json.ts`/`format.ts`, themselves fsm-cli's reader): the same problems, messages, lines and derived ids; both files written deterministically and byte-identical to the other editions (`Num.format` prints numbers like JavaScript). `MachineFiles.kt`: a document's state (the two texts and the model) and writing a model into one (an edit the format can't hold is refused).
  - `Xmi.kt` + `XmlTree.kt`: reading old files (XMI with UML DI); `Conversion.kt` converts them, a group linked by submachines at a time. Nothing writes XMI. `Load.kt`: a model from a file's text, either format.
  - `Compare.kt`, `Merge.kt`, `Sessions.kt`: comparing two versions, conflict markers and taking a side, the logic of the diff and merge panes.
  - `Validation.kt`, `Expressions.kt` (text grammar), `Labels.kt` (transition label syntax), `Geometry.kt` (compartments, regions, routes, labels; also used to convert the UML DI region shapes of old files), `DiagramSession.kt` (every editing operation, calling the `onCommitted` listeners), `Tools.kt`, `SvgExport.kt`, `ClipboardJson.kt` (same clipboard JSON as the other editors, and a small JSON reader), `Workspace.kt` (hrefs, machine summaries, submachine resolution), `Trace.kt` (the Trace Player: log formats, replay, and `TraceSession`, the logs, timeline and cursor).
- `plugin` (IntelliJ Platform Gradle Plugin 2.x, compiled against IC 2024.3):
  - `FsmEditorProvider` (`PLACE_BEFORE_DEFAULT_EDITOR`) adds the Diagram tab before the Text tab. `.fsm` files are `FsmFileType` (a `JsonFileType`), old ones `OldFsmFileType` (XML, told apart by their content); `*.fsm.layout` is mapped to JSON. `FileSource` (`editor/DiagramSource.kt`) is a machine over the IDE's documents of its two files: its state is read from their texts (the same texts give the same state object), a diagram edit writes both documents as one `WriteCommandAction`, and save, the modified mark and undo/redo are the IDE's (`FsmFileEditor` implements `DocumentReferenceProvider` over both). Opening changes nothing; an old file is converted at the first edit, and the files linked to it when it is saved; an unreadable layout file is replaced only after asking, at the first edit. `DiagramPane` is a diagram over a source (validation in a non-blocking read action against the machines found by `FsmWorkspace`, the Trace Player's ids mapped with `derivedIds`). A file with merge conflicts opens as the diagram merge in its Diagram tab (`FsmFileEditor`: result, incoming, current); Compare as Diagrams is a `FrameDiffTool` (`editor/DiagramDiff.kt`) shown by the IDE's diff view; both link panes through Core's `MergeSession`/`DiffSession`, and `services/Git.kt` runs git.
  - `editor/`: Swing built in code. `DiagramCanvas` paints with Java2D and hit-tests geometrically; `PropertiesPanel` rebuilds itself per selection; `Theme` maps IDE/editor-scheme colors; `ToolIcons` draws the toolbox icons.
  - Copy/Cut/Paste/Delete come from the IDE actions through `DiagramCanvas.uiDataSnapshot` (only while the canvas has the focus); other keys are handled by the canvas.
  - `services/FsmAnnotator` reports the problems of a model file that can't be read, and validation at the line of each element (an old file's at its `xmi:id`), in the Text tab and the Problems view; `FsmSchemas` gives the Text tab the JSON Schemas (fsm-cli's from `cli/schemas`, the layout file's from the plugin's resources); `FsmResources` makes the XML support ignore the XMI/UML namespaces of old files. `FsmWorkspace` also renames or moves a layout file with its model file.
  - `trace/`: `TracePlayerService` (project service) runs a `TraceSession` (polls the logs' size and time to follow them, play timer, machines of the project and open documents) and hands each open diagram its `TraceView`, drawn by `DiagramCanvas`; `TracePlayerWindow.kt` is the Trace Player tool window.
  - `codegen/FsmCli.kt` runs `fsm write <file> --template <jinja> --out <dir>` and parses `wrote …` lines, `file:line: severity: message` problems and fsm's own `fsm: …` messages (shown when it fails, such as a template it refuses). The release workflow bundles `fsm` and its templates in `plugin/cli/<platform>/` and the model file's schema in `plugin/cli/schemas`, from the archives of the fsm-cli release pinned by `FSM_CLI_VERSION`, and runs the tests against its cases archive. `CodeGeneration.generate` is the whole flow; output goes to the FSM Code Generation tool window.

## Project rules

- Keep parity with the VS Code and Visual Studio editions: text grammar, validation rules and messages, file format (both files, byte for byte), clipboard JSON. The model file's reader and validator are checked against fsm-cli's test cases (`CasesTest.kt`), the layout reader against the VS Code edition's layout test files (`fixtures/layout`). `core/src/test/resources/fixtures` holds reference results from VS Code, the same as the Visual Studio edition's: regenerate them from the umbrella repo with `node parity/fixtures.mjs` when the reference changes (see fixtures/README.md), and check the three editions write the same files with `node parity/check.mjs`. `core` ports the Visual Studio edition's C# Core file for file, so port a change from there. `Geometry.kt` mirrors `media/editor.js` of the VS Code edition: compare it by hand, for example with the screenshots from `:plugin:test`.
- **Text grammar:** behaviors are argument-less calls separated by `;`; conditions combine calls with `!`, `&&`, `||` and parentheses; `else` only on choice/junction branches; triggers are event names or `after(<number><ms|s|m|h>)`. The editor refuses invalid text, and the validator reports it.
- **Out of scope:** state machine extension/inheritance and the transition-oriented notation.
- Don't reimplement code generation: templates and the code model belong to fsm-cli.
- `.fsm` files hold no model hash: fsm-cli computes it from the file.
- Core must not reference IntelliJ classes. Keep the plugin free of internal, override-only and experimental API: `verifyPlugin` must report "Compatible" with no such usages (Kotlin compiles with `-jvm-default=no-compatibility` so implementations of platform interfaces don't re-declare their default methods). Kotlin API level stays at 2.0 (the stdlib of 2024.3).
- User-facing docs: `README.md`, `docs/UML-CONFORMANCE.md` (update when behavior or rules change), `docs/CODEGEN.md`.
